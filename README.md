# Working with Claude: Claude Code hands-on

The afternoon session, "Claude Code, zero to expert", is three hours in six parts. Parts 3, 4 and 5 are hands on keyboard, and all three run in this repository. Everything you need is here: the set-up, the three exercises, the sample app, the tickets and the reference files.

## Start here

1. **Set-up** (before Part 1, five minutes): [`workshop/SETUP.md`](workshop/SETUP.md). Four paths: local install, GitHub Codespaces (nothing to install), Claude Code on the web, or pair up. Ends with the three "are you green" checks.
2. **Pre-work** (the night before, 15 minutes): [`docs/PRE-WORK.md`](docs/PRE-WORK.md). Install, clone, run the tests, and keep the brief and the definition of done handy.

## The app: ops-dashboard

The operations dashboard at Marlowe & Finch, a coffee-equipment company. A small
Spring Boot REST API over a PostgreSQL database, plus a plain-JavaScript page that
lives on a wall screen in the operations office: four KPI tiles, two charts, the
late deliveries of the period, and the vendor contracts coming up for renewal.

Two sentences to explain it: the Java side reads `orders`, `deliveries`, `tickets`,
`carriers` and `vendors` with plain SQL (Spring JDBC, Flyway migrations, no JPA) and
serves read-only JSON under `/api`; the frontend in `src/main/resources/static/`
calls those endpoints with `fetch` for a date range and draws the tiles, two inline
SVG charts, the table and the list.

The data is fictional and generated by `tools/make_seed.py`: about 1,900 orders and
deliveries over the 90 days before 21 September 2026 across four carriers, 600
support tickets, and eight vendor contracts. One carrier, Kessler Logistics, has been
slipping all summer. The dashboard is meant to make that visible.

### Run it with PostgreSQL (the default)

```bash
docker compose up -d db      # PostgreSQL 16 on localhost:5432, database/user/password "ops"
./mvnw spring-boot:run       # then open http://localhost:8080
```

Flyway creates the schema and loads the seed on first start (`V1__schema.sql`,
`V2__seed.sql`). The database keeps its data between runs; `docker compose down -v`
wipes it. Connection details can be overridden with `DATABASE_URL`, `DATABASE_USER`
and `DATABASE_PASSWORD`.

### Run it without a database (the `demo` profile)

```bash
SPRING_PROFILES_ACTIVE=demo ./mvnw spring-boot:run
```

Same migrations, same seed, in an in-memory H2 database in PostgreSQL mode. Use this on
a laptop without Docker and in Claude Code on the web. The tests always run on it.

### Today is 2026-09-21

The app's clock is pinned to 21 September 2026 (property `ops.today`, bean in
`ClockConfig.java`) so the default date range, the "days until renewal" figures and
the tests all agree with the seed data whatever the real date is. Every default range
is "the last 30 days ending today".

### Test it

```bash
./mvnw test                 # Java: 54 tests (JUnit 5, H2, MockMvc)
npm install                 # once
npm test                    # Frontend: 45 tests (Jest + jsdom)
```

### The data connection (Lab 2)

`.mcp.json` at the root registers a `postgres` MCP server that Claude Code starts on
demand with `npx -y @modelcontextprotocol/server-postgres`. It is read-only (every
query runs in a `READ ONLY` transaction) and points at the local compose database,
`postgresql://ops:ops@localhost:5432/ops`. In Codespaces the dev container shares the
database's network, so the same address works there. `/mcp` inside `claude` shows it
as `postgres`. Without Docker, the same question can be answered from
`docs/data/deliveries-last-30-days.csv`.

### Stack

- Java 17, Spring Boot 3.2, Spring JDBC, Flyway, PostgreSQL driver, H2 for the demo profile and tests; Maven (wrapper included, no local Maven needed)
- Vanilla JavaScript, HTML and CSS; no build step, no framework; charts are inline SVG
- Jest with jsdom for the frontend tests; the harness lives in `src/test/javascript/setup/loadApp.js`

### API

All endpoints are `GET`, return JSON and are read-only. `from` and `to` are ISO dates
(`2026-09-14`) and default to the last 30 days ending today. `limit` defaults to 20.

| Path | Returns |
|------|---------|
| `/api/health` | `{"status":"UP","today":"2026-09-21"}` |
| `/api/kpis?from&to` | On-time delivery rate, open tickets, revenue and order count for the range |
| `/api/deliveries/on-time?from&to` | Delivered, on-time and rate per carrier (deliveries that arrived in the range) |
| `/api/deliveries/late?from&to&limit` | Late deliveries, worst first: order, carrier, promised and delivered dates, days late |
| `/api/tickets/by-category?from&to` | Tickets opened in the range per category: still open, and total |
| `/api/vendors` | Every vendor with annual spend, contract end, notice days, owner, days until contract end and whether that is inside the notice window |

`from` and `to` must be ISO dates (`YYYY-MM-DD`) with `from` on or before `to` and at
most 366 days apart; `limit` must be an integer from 1 to 500 (default 20). Bad input
returns `400` with `{"errors": [...]}` listing every problem (TODO-232).

Workshop material is in `workshop/` and `docs/`.
